## Context

当前系统使用 Spring Security + JWT 做认证。当 token 过期或无效时，Spring Security 的 `authenticationEntryPoint` 被触发，调用 `writeError` 方法返回错误信息。但该方法始终将 HTTP 状态码设为 200，导致前端 axios 响应拦截器的 401 错误处理分支（`error.response.status === 401`）永远不会被执行。

前端两个应用（Admin / H5）的 axios 实例都只在**错误拦截器**中处理 401 跳转，未在**成功拦截器**中对业务错误码做防御性处理。

## Goals / Non-Goals

**Goals:**
- Token 过期/无效时，Admin 和 H5 均能清理登录态并自动跳转登录页
- 用户能看到明确的"登录已过期"提示

**Non-Goals:**
- 不引入 token 自动刷新机制
- 不改变 token 存储方式（仍使用 localStorage）
- 不修改登录/登出流程的 UI

## Decisions

### 决策 1：后端修复为主，前端加固为辅

**选择**：同时修改后端 `writeError` 的 HTTP 状态码和前端的成功拦截器业务错误码处理。

**理由**：
- 后端返回正确的 HTTP 状态码是 RESTful 基本实践，且能从协议层面触发前端已有的 401 处理逻辑
- 前端加固提供了纵深防御——即使将来其他后端接口在 HTTP 200 下返回业务错误码 401，前端也能正确处理
- 两处修改互不依赖，可分步部署

**替代方案**：仅修改前端成功拦截器，不碰后端。
- 否决理由：治标不治本，且无法保证所有调用方都检查了业务错误码。后续新增接口也可能重现此问题。

### 决策 2：`writeError` 根据 code 参数设置 HTTP 状态码

**选择**：`writeError` 方法将 `code` 参数同时用于响应体和 HTTP 状态行。

```java
res.setStatus(code); // 之前: res.setStatus(200)
```

**理由**：调用方传入的 `code` 已经是语义化的错误码（401/403），直接复用到 HTTP 层，无需额外参数。

### 决策 3：H5 成功拦截器增加业务错误码检查

**选择**：在 H5 的 `response.use` 成功回调中增加 `res.code !== 0` 检查，与 Admin 端对齐。

**理由**：H5 当前完全不做业务错误码检查，任何 `code !== 0` 的响应（包括 401、403 等）都会被组件当做成功数据处理，可能导致运行时异常。

## Risks / Trade-offs

- **[低风险] 前端 401 处理被双重触发**：后端返回 HTTP 401 → 前端错误拦截器处理 → 同时成功拦截器也可能检测到（不适用，因为 HTTP 401 走错误分支）。→ 实际上不会发生，因为 HTTP 401 直接进入错误拦截器 `error` 回调，不会进入成功回调。后端的修改使认证错误走 HTTP 错误分支，前端的加固仅对"HTTP 200 但业务 code 401"的情况生效，两者互不干扰。

- **[低风险] 已有前端调用方行为变化**：Admin 成功拦截器中 `res.code !== 0` 时 return `Promise.reject(new Error(...))`，调用方的 `.catch()` 会收到通用的 Error 对象而非带有响应信息的错误。→ 本次不改动这个行为，仅新增 401 的特殊处理（放在通用 `code !== 0` 检查之前），不影响其他业务错误码的现有处理。

## Migration Plan

1. 修改后端 `SecurityConfig.writeError`，重启后端
2. 修改 Admin 前端 `request.js` 成功拦截器，构建部署
3. 修改 H5 前端 `request.js` 成功拦截器，构建部署
4. 验证：登录后等待 token 过期，刷新页面，应自动跳转登录页并显示"登录已过期"提示

**回滚**：每处修改独立可逆，分别回滚对应文件即可。

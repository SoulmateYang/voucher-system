## Context

系统中员工标识有两个字段：`username`（原始工号，NOT NULL，自 V1 起存在）和 `employeeNo`（后加工号列，V4 迁移新增，DEFAULT NULL）。存量数据 `employee_no IS NULL`，导致前端表格「工号」列显示为空。

卡券发放流程中，管理员需按工号或姓名查找员工后发放卡券。后端已有 `GET /api/v1/employees?keyword=` 搜索接口（支持工号/姓名/手机号/部门模糊匹配），但前端 BatchManage.vue 的发放对话框未接入该能力，仅提供手工输入框。

## Goals / Non-Goals

**Goals:**
- 员工管理表格「工号」列始终有值：优先展示 `employeeNo`，回退至 `username`
- 卡券发放时管理员可通过关键字搜索并选择员工，自动填充工号和姓名
- 保持与系统现有 UI 风格一致（Element Plus）

**Non-Goals:**
- 不改动后端 API（已有足够能力）
- 不修改数据库 schema
- 不增加员工信息编辑/新增功能
- 不在 H5 端做对应修改（H5 不涉及卡券发放操作）

## Decisions

### 决策 1：Bug 1 修复方式 —— 前端模板回退 vs 后端数据补齐

**选择**: 前端表格列使用自定义模板 `row.employeeNo || row.username`，同时提供可选的 SQL 迁移脚本补全存量数据。

**理由**:
- 前端修复立即可见，零后端部署
- 项目已在编辑弹框中采用相同回退逻辑（`EmployeeManage.vue:236`），本次仅对齐表格列，保持一致性
- 可选 SQL 脚本确保长期数据完整性

**替代方案**: 仅跑 SQL 一次性补齐，不改前端。
- 否决理由：无法防御未来再次出现 NULL 的情况（如直接 SQL 插入）。前端防御性回退更稳健。

### 决策 2：Bug 2 修复方式 —— 内联搜索选择器 vs 独立弹窗

**选择**: 在发放卡券对话框中嵌入内联搜索输入 + 下拉结果列表，替换当前的手工输入框。

**理由**:
- 操作流畅度高：输入 → 即时搜索 → 点选 → 自动填充，在一个界面完成
- Element Plus 的 `el-autocomplete` 组件原生支持此模式
- 不引入额外的弹窗层级

**替代方案**: 新增一个独立的「选择员工」弹窗（Dialog），带搜索 + 表格 + 确认按钮。
- 否决理由：增加操作步数（打开弹窗 → 搜索 → 勾选 → 确认 → 关闭），对批量发放多个员工时尤为繁琐。

**替代方案**: Debounced 远程搜索 + 下拉列表，不在输入时自动显示结果。
- 否决理由：与本方案一致，仅交互细节有所不同。将采用 debounce (300ms) 避免频繁请求。

### 决策 3：搜索结果展示格式

**选择**: 下拉项展示为「工号 | 姓名 | 部门」，例如 `EMP001 | 张三 | 技术部`。

**理由**: 提供足够信息区分同名员工，格式与表格列对齐。

## Risks / Trade-offs

- **[低风险] 回退显示可能掩盖数据问题**: 若 `employeeNo` 和 `username` 同时为空（实际上 `username` 有 NOT NULL 约束，不会发生），工号列将显示空。→ 模板中增加最终回退 `|| '-'`，确保永不为空。

- **[低风险] 搜索输入频繁请求**: 用户快速输入时可能触发多次 API 请求。→ 使用 debounce (300ms) 平滑请求频率，且搜索结果数量上限为 10 条。

## Migration Plan

1. 修改 EmployeeManage.vue 表格「工号」列模板 → 构建部署 Admin 前端
2. 修改 BatchManage.vue 发放对话框，接入员工搜索 → 构建部署 Admin 前端
3. （可选）执行 SQL 脚本补齐 `employee_no` 存量数据

**回滚**: 每处修改独立可逆，回滚对应文件即可。
